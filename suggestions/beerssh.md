# fmake, evaluated against beerssh

Written 2026-08-04, from a trial against a copy of the tree. Per
`build-and-commit.md`'s standing instruction that projects which could adopt
fmake should say whether they would.

## What beerssh is, for sizing

An SSH client with a real terminal emulator, one codebase for Linux desktop
and Android. Roughly:

- ~134 sources under `src/`, in six subdirectories (`input`, `model`,
  `platform`, `ssh`, `term`, `ui`), plus `tests/`.
- Two binaries from one source tree: the app, and a test binary that takes
  every source **except** `src/main.cpp` -- otherwise two `main()`s.
- Qt 6 Widgets throughout, so 26 headers and 21 test headers need `moc`.
- One vendored submodule, `libvterm`, built as a static archive from a
  patch set applied at build time.
- Cross-compiled for Android (two ABIs) in the same checkout, via qmake and
  `androiddeployqt`.
- Packaged as two `.deb`s and an `.apk`.

A hand-written top-level `Makefile` that recurses into qmake-generated ones.

## The trial

`fmake --explain`, then `--widen-all`, against a copy of the tree with the
submodule in place. In order:

**1. `tests/main.cpp` wants a target called `tests`, which is a directory.**
Same collision fuzzypickles reported. `[target.tests] name = "beerssh_test"`
in `fmake.toml` fixed it. Worth noting the first `fmake.toml` I wrote used
`[program.*]`, which is a reasonable guess from the vocabulary in the output
-- the error named the valid sections, so it cost one attempt rather than a
search through the docs.

**2. The include-path model is the blocker, and it is one rule.** 84 files
failed to compile, every one of them like this:

```
src/model/session.h:8:10: fatal error: model/profile.h: No such file or directory
src/ui/theme.h:7:10: fatal error: platform/platform.h: No such file or directory
```

This project includes its own headers **subdirectory-qualified from the
source root** -- `#include "model/profile.h"`, not `#include "profile.h"` --
which is a common C++ convention and is what stops `screen.h` and
`session.h` from being ambiguous across six directories. fmake adds `-I` for
every directory that *contains* sources:

```
-I. -Isrc/input -Isrc/model -Isrc/platform -Isrc/ssh -Isrc/term -Isrc/ui -Itests
```

but not `-Isrc`, their common parent. So every qualified include misses. The
project's own build says `INCLUDEPATH += src` and nothing else.

This looks cheap to fix and would be the single highest-value change for
this tree: add the common parent of the source directories alongside the
leaves. It cannot break the flat case, where the parent is already `-I.`.

**3. Two binaries over one source tree, minus one file, cannot be
expressed.** The test binary needs all of `src/` except `src/main.cpp`.
`[target.*]` carries link-side keys, and there is no "exclude" among them,
so `src/main.cpp` is pulled into `beerssh_test` and the app has no target of
its own at all -- `--explain` listed `beerssh_test` and four vendored
programs, and no `beerssh`. A per-target exclusion, or a way to say "this
source roots its own program and belongs to no other", would cover what is
probably a common shape: an app and its test binary sharing everything but
`main`.

**4. The vendored submodule's own programs get built.** `unterm`,
`vterm-ctrl`, `vterm-dump` and `harness` all linked successfully -- they are
libvterm's upstream tools, in `vterm/bin/` and `vterm/t/`. This project
treats vendored code as exempt and builds only the library from it. They
were the only four things that *did* link.

**5. Symbol reachability does not work for a Qt program.** `--explain`
reported **547** sources as "defines nothing reachable", including every
`moc_*.cpp`. That is correct as far as symbols go and wrong about the
program: a `QObject`'s slots are reached through the meta-object system, and
a QtTest class is reached by `qExec` walking its metadata, so nothing
references them directly. `--widen-all` is the documented escape and it
works, but it also pulls in (4), so the two interact: the flag that makes a
Qt tree compile is the flag that builds the vendored tools.

If there is room for a heuristic, "a translation unit generated by `moc`, or
one whose header carries `Q_OBJECT`, is always reachable" would cover this
without `--widen-all`.

**6. Tests are built by the default build.** As fuzzypickles reported.
`build-and-commit.md` says the default target does not build tests, and this
project relies on that -- `make test` is what builds and runs them.

## What worked, and is worth saying

**`moc` support is the reason this trial got as far as it did.** fmake found
all 26 `Q_OBJECT` headers in `src/` and 21 in `tests/`, generated and
compiled them, with no annotation and no configuration. That is the single
hardest part of building a Qt project without a build file, and it was
invisible -- it simply worked.

**Qt module discovery is likewise automatic and complete.** It resolved
Core, Gui, Widgets, Network, DBus, Test and Concurrent, and found libsecret,
glib and libsixel include paths, all from the sources. The flags it produced
match what qmake produces, module for module.

**The errors name the remedy.** Every one of the failures above printed what
was wrong, which file, and what to change. None of them cost a debugging
session -- (2) took one compile to identify because the error was a plain
missing include with the qualified path in it.

## `--eject`, tried separately

Worth its own note, because for a tree like this one it is the more likely
route: keep the top-level `Makefile` that does the patching, the Android
build and the packaging, and let fmake work out the compile step once.

It works, and the output is good. `OBJDIR` is the variable name, which is
the one `build-and-commit.md` asks for. The moc section is driven by
`Q_OBJECT` in the source rather than a list, and says so. `-MMD` is emitted
for all 34 compile rules and the `.d` files are `-include`d back, so the
first of that file's three dependency rules is satisfied -- which is the one
that matters most and the one most often missed.

Three things about the ejected file:

**`clean:` does `rm -rf $(OBJDIR) ...` unguarded.** This is worth changing.
`build-and-commit.md` treats it as a safety property rather than a style
point: an unset or mistyped variable in `rm -rf $(VAR)` is how a clean
target eats something it should not, and the ejected file invites exactly
that -- it is handed to people to edit, and `make clean OBJDIR=...` is a
normal thing to type. A guard costs four lines: refuse an absolute path,
refuse one containing `..`, refuse `.`. (beerssh had the same bug in its own
`Makefile` and fixed it the same week as this trial, which is why it is
recognisable rather than theoretical.)

**No `.SECONDARY`, and none needed -- but for a reason worth writing down.**
That rule exists because a *bare* `.SECONDARY:` lets Make skip rebuilding a
missing intermediate. The ejected file emits one explicit rule per object
rather than pattern rules, so nothing is an intermediate and the hazard does
not arise. Saying so in the generated header would stop somebody adding a
bare `.SECONDARY:` later to be helpful, which would reintroduce it.

**It inherits the include-path defect**, naturally -- the ejected `CXXFLAGS`
is the same flag list. So fixing (2) fixes both routes at once.

Minor: the `-include` line is a single line naming every object explicitly.
It works, and the header invites hand-editing, which that line makes
unpleasant. `$(OBJS:.o=.d)` would read better in a file whose whole premise
is that it is now yours.

## One formatting bug

`--explain` loses the separator between a filename and its message once the
name is long enough:

```
    tests/tab_status_test.cpp       defines nothing reachable
    .fmake/moc/src/input/moc_input_router.cppdefines nothing reachable
```

The column pad is computed from a width the generated moc paths exceed. A
minimum of one space would do it. It matters more than it looks on this tree
because 547 of those lines went past the pad.

## Verdict

**Not viable for beerssh today, and (2) is most of the reason.** With the
common parent on the include path, the trial would have got past 84 of its
failures in one step and the remaining questions would be real design ones:
how to exclude a source from a target, and what to do about vendored trees
that carry their own programs.

Worth re-testing if the include-path rule changes.

**And it would still only replace part of this build.** Compiling is one of
six things the top-level `Makefile` does: it also applies four patches to
the vendored submodule and fails loudly if any stops applying, cross-builds
for two Android ABIs through `androiddeployqt`, stages fonts into the APK's
assets, builds two `.deb`s with dependencies derived by `dpkg-shlibdeps`,
and runs six `check-*` gates. fmake replacing the compile step would leave
that Makefile in place, which is a fair trade only if the compile step is
where the trouble is -- and here it is not. That is context for the verdict,
not a criticism: a build tool that does not do those things is not supposed
to.
